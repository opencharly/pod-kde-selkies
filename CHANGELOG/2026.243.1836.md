# 2026.243.1836 — chore(deps): advance stale candy pins to current

## Summary

This repo's candy pins lag the versions the rest of the org resolves, and because a published tag
embeds the pins it carried **at mint time**, that cost lands on every consumer rather than here.

Traced from a consuming closure by walking the transitive ref graph — 587 pinned refs — back to
the tag that *introduces* each stale version. This repo is one of those tags:

```
-            - '@github.com/opencharly/pod-selkies:v2026.243.0720'
+            - '@github.com/opencharly/pod-selkies:v2026.243.1737'
-            - '@github.com/opencharly/pod-dbus:v2026.239.1555'
+            - '@github.com/opencharly/pod-dbus:v2026.243.1831'
```

A project that pins this repo gets a `resolved to multiple versions` warning it **cannot clear
from its own tree**: the stale pin lives inside this repo's published tag, not in theirs.
`charly box reconcile` there rewrites only that project's own pins and reports no change against
it, so the remedy the workflow rule prescribes cannot reach this.

## Why a full alignment rather than only the one flagged pin

Advancing pins piecemeal in a stale tree multiplies skew — measured elsewhere in this campaign, a
partial advance took a closure from 2 warnings to 26 before coming back down. Every dependency of
this repo already has a current tag upstream, so aligning **all** of them lands consistent, where
advancing only the flagged one would leave this tag introducing the next conflict.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**:

```go
for _, c := range cands {
    if c.Version != best.Version {   // <- entity version, not the git tag
        warn("Warning: candy %s resolved to multiple versions; …")
```

Identical entity versions across different git tags resolve silently, on tag freshness. Bumping
the stamp for a pin-only change would therefore **manufacture** the exact warning this PR
removes, for every consumer still pinning an older tag of this repo.

## How tested

```
$ git diff --stat origin/main...HEAD
charly.yml | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)
```

Every replacement tag was confirmed to exist before pinning, via `git ls-remote --tags --refs`
against each owning repo.

The effect is only observable in a consuming closure — that is where two materializations of a
candy meet and the arbiter picks between them. Measured there with a stock `task build:binary`
charly: this campaign's first wave took that closure from **12 conflicts to 4**, and these
remaining ones were traced to the tags introducing them, of which this repo is one.

## Rulebook compliance

- **R1 (RCA)** — traced to the mechanism (the arbiter compares per-entity `version:`) and to the
  introducing tag via a transitive graph walk, not guessed from a text search. An earlier
  cache-wide grep in this campaign produced false owners; the graph walk replaced it.
- **R3 (no duplication)** — pins only; no manifest logic touched.
- **R4 (no workarounds)** — advanced at the source. Pinning around it downstream is impossible by
  construction, which is why the change belongs here.
- **R5 (delete legacy)** — the stale pins are replaced, not supplemented.
- **R6 (git safety)** — feature branch, no force-push, no hook bypass.

## Change classification

- **Change class:** dependency pins — `@github` refs only. No packages, services, plan steps, or
  entity-version change.
- **Verification gate:** `git diff --stat` on the committed tree plus `git ls-remote` confirmation
  that every target tag exists; cross-repo effect measured in a consuming closure.
- **Attribution tier:** `analysed on a live system` — the skew this fixes was measured live in a
  real consuming closure with a stock charly build and the tags verified live. Short of the
  runtime tier because a pin-only change ships no runtime path of its own to execute.
