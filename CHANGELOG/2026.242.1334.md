# 2026.242.1334 — fix: advance the pod-selkies pin so the graph declares one version

## Summary

This candy's newest tag pins `pod-selkies` at `v2026.240.2150` — a tag that reaches
`layer-python v2026.235.2057`, which references the candy `pixi` by **bare name**. `pixi` became the
separate repo `opencharly/layer-pixi` in the candy cutover, so that chain fails with
`unknown candy "pixi"`. `pod-selkies` fixed it in `v2026.242.1235`; this pin advances onto that.

It is also the last holder of the old `pod-selkies` in the selkies graph: with the pixelflux layers
and `pod-selkies-core` already advanced, this candy is why consumers still see two versions.

Leaving it stale has a second cost beyond the error: once any sibling advances `pod-selkies` while
this candy does not, the graph carries two versions of the same candy and charly reports

```
Warning: candy github.com/opencharly/pod-selkies resolved to multiple versions;
         using newest … ignoring …
```

`PickCandyVersion` is the sole candy-version arbiter and picks newest project-wide, so resolution
stays correct — but it is charly's tie-break covering for a stale declaration, which is exactly
what this PR removes.

**The schema line and the CI charly pin move with it, as one atomic change.** `charly box validate`
— the gate for this change class — refuses to run until the schema is migrated:

```
schema 2026.240.1943 is required (found "2026.232.0520"). Run: charly migrate
```

and the migration is precisely what makes the CI's pinned charly too old:

```
config schema 2026.240.1943 is newer than this charly supports
```

Landing either half alone leaves the repo broken in one direction or the other.

## Change classification

**Change class:** candy/box-config **+ CI-config** — two files: `charly.yml` (schema version, candy
`version:`, the `pod-selkies` ref) and `.github/workflows/deploy.yml` (the charly clone pin
`v2026.238.1242` → `v2026.241.1130`). **This PR does change a workflow.** No Go, no schema
authoring, single repo.

**Verification gate:** `charly box validate` on the final committed tree for the candy half; for the
CI half, the pin is set to a value already running green against this exact schema in three sibling
repos, with this PR's own `candy` job as the direct proof.

**Breaking change + rollback:** none — a pin advance onto a published tag whose only difference is
that it pins what it already depended on. Rollback is a plain revert of the commit; reverting only
one half re-creates the mismatch.

**Producer → consumer order:** satisfied — `pod-selkies v2026.242.1235` and charly `v2026.241.1130`
are both merged, tagged and published.

Zero bytes on stdout **and** stderr.

### Why `CHARLY_PLUGIN_ONLY=1`, with the RCA rather than a dismissal

Run without it, this gate emits one warning, and it is charly's own deliberate signal, so it gets a
root cause rather than a hand-wave. `plugin_loader.go:434 warnSkippedFHSPlugins()` fires when the
running binary is not at `/usr/bin`/`/usr/local/bin` **and** `/usr/lib/charly/plugins` holds
`.providers` manifests. Its own comment gives the intent: those plugins *"were built against a
different charly version (issue #328)"*, so a dev binary must not load them, and the warning exists
to make the skip visible instead of silent.

```
(a) What would have been loaded:  /usr/bin/charly version -> 2026.187.2228
    …against a tree requiring schema 2026.240.1943 — 55 days and a schema epoch apart.
    Refusing to load them is CORRECT; loading them would be the defect.

(b) Caused by this PR? No — it fires identically on an untouched clone of main.

(c) Does the skip weaken this gate? Provably not. plugin_loader.go:454 documents
    CHARLY_PLUGIN_ONLY=1 as "the supported way to resolve AS-IF-UNPACKAGED" — it DROPS
    the FHS path from the search, masking nothing, and its output is byte-identical to
    the normal run minus that one line.
```

So this is charly's documented seam for a dev binary, not output suppression.
